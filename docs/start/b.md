# Context briefing for a new agent

Read this first if you are a Claude Code or Codex session that has just been pointed at this repository. It tells you what the project is, what state it is in, how to work without breaking the others, and what "done" means. Then read your role file in `docs/agents/`.

## 1. The situation
- This repository is a single-file web application, the **Asset Knowledge Platform**: a knowledge hub for a process plant. It puts P&IDs, equipment drawings, plot plans, interlock logic, one point lessons (OPLs), datasheets and maintenance history in one place, with a cited AI assistant, predictive maintenance, scenario and hazard simulation, and 3D views.
- It was first built for one plant (an LLDPE unit, case `lldpe`) for a university competition. The team is now in the **final round of a hackathon** with a **different plant-related case**, to be built **in under a day**, by a human team working with several AI agents at once.
- The app is an engine plus a **case pack**. A new plant means a new folder `cases/<id>/`, not new engine code. The engine already does everything listed in `docs/CAPABILITIES.md`. Extra features for the new brief are the only real engine work.

## 2. Vocabulary
| Term | Meaning |
|---|---|
| set | one main machine and its attached items (pump, column, heater ...), numbered 1..N. Everything is organised by set |
| tag | equipment or instrument identifier, e.g. `P-101A`, `PSLL-101` |
| P&ID | process and instrumentation diagram. Generated from data unless drawn by hand in `cases/<id>/geo/pid.js` |
| GA | general arrangement drawing of one machine, with a parts list and nozzle table |
| OPL | one point lesson: a one page lesson with procedure steps and troubleshooting rows |
| interlock, SEQ, cause and effect | the trip logic of a set: initiators (trips), voting, effects, permissives |
| work order (WO) | one maintenance record. The history drives reliability and prediction |
| case pack | the folder `cases/<id>/` holding all plant data |
| geo | optional hand-drawn geometry files; missing ones are generated by `src/modules/auto.js` |
| smoke test | `tests/smoke_case.js`, a case-neutral check that any pack loads and works |

## 3. State of the repository
- Default case `lldpe` (8 sets, 211 work orders, 131 evaluation questions, hand-drawn geometry). `cases/mock-cdu` is a 7-set crude distillation unit built only from `plant.json`: the dry run of the new-case process. `cases/_template` is the smallest starting point.
- Build: `python3 build.py [case-id]` makes `dist/index.html` (one file). Generated files are never committed.
- Tests that must stay green: `npm run test:quick`, `node tests/smoke_case.js <built html>` on `lldpe`, `mock-cdu` and the new case, `node tests/layout.js --quick --strict`.
- Deliverable builders outside the app (`finance/`, `deck/`, `manual/`) still carry the first case's content.

## 4. How the app is put together (one page)
- `build.py` joins `src/base.html`, `src/modules/*.js`, `src/data/eqclass.json` and the chosen case pack into one HTML file, then checks the scripts parse.
- `cases/<id>/`: `kb.json` (sets, assets, documents, text chunks, instruments, OPLs, nozzles, parts, data issues), `dsil.json` (datasheets, interlocks), `ga.json`, `mh.json` (work orders), `eval_cases.json` (questions with known answers), `case.json` (names and wording), `geo/*.js` (optional drawings).
- A new case is written as a compact `plant.json`, or as fragments in `plant/case.json` and `plant/sets/NN-tag.json` (one file per set, so people do not collide), and compiled by `python3 tools/pack_build.py cases/<id>`.
- Netlify functions in `netlify/functions` give the shared database, access codes and the Gemini proxy. The page works without them (local only).
- Details: `docs/ARCHITECTURE.md`, `docs/CASE_PACKS.md`, `docs/CONTRACT.md`.


## 6. Rules that apply to everyone

2. **Shared hot files** (`build.py`, `src/base.html`, `tests/regress.js`, `tests/smoke_case.js`, `docs/CONTRACT.md`) are changed only by Claude A (the integrator), or by you after writing "taking build.py" in `docs/TASKS.md`. With two Claudes read `docs/TWO_CLAUDES.md` for the day-to-day routine.

# Workflow for several agents on one repository

```
main             protected. Only the human merges to it, when a demo-ready version exists
 └─ integration  where all work meets and is tested together
     ├─ a/<topic>      Claude A (data and intelligence)
     ├─ b/<topic>      Claude B (pages and visuals)
     └─ codex/<topic>  Codex (deliverables, tests, docs)
```

## Rules
1. Each agent works on its own branches, named with its prefix, branched from `integration`.
2. Merge into `integration` every 1 to 2 hours, or whenever a piece works, never with red tests. Use merge commits, not rebase. Never rewrite pushed history.
3. The **integrator** (one session) does the merging with `tools/integrate.sh` and is the only one who resolves conflicts in shared files. It does little feature work.
4. Before starting a piece of work, pull `integration` and read `docs/TASKS.md`. Before pushing, pull again.
5. Two agents never edit the same file. Ownership is in the role files. If a task needs a file you do not own, write the request in `docs/TASKS.md` for its owner.
6. The human merges `integration` to `main`.

## Integration cycle (the integrator runs this)
```
tools/integrate.sh --report            # what each branch changed, and which files overlap
tools/integrate.sh a/topic b/topic codex/topic    # merge, build, test; stops and reports on a conflict
```
Then: read the report, screenshot the dashboard and two equipment pages (`node tools/case_shots.js dist/index.html /tmp/shots --quick`), tell the owners in `docs/TASKS.md` what to fix, and push `integration`.

## Message board
`docs/TASKS.md` is the only channel between sessions. Sessions cannot see each other's chat. One line per task: id, owner, status (`todo`, `doing`, `blocked`, `done`), files, and a note.

## When a merge conflicts
- In a file one agent owns: that agent's version wins; re-apply the other change by hand if it is still needed.
- In a shared hot file: the integrator merges both by hand, runs the tests, and notes it in `docs/TASKS.md`.
- Never resolve by deleting the other agent's work.
